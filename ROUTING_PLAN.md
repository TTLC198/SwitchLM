# План развития маршрутизации

## Цель

Сделать выбор между Luna и Sol независимым для каждого нового запроса, объяснимым и измеримым, а затем подготовить данные для обучаемого маршрутизатора.

## Приоритет 0 — корректность текущего алгоритма

**Статус: выполнен.**

### 1. Зафиксировать проблему накопленного контекста

- Добавить регрессионный тест: сложный предыдущий запрос и простой последний запрос должны маршрутизироваться в Luna.
- Добавить обратный сценарий: простой предыдущий запрос и сложный последний запрос должны маршрутизироваться в Sol.
- Проверить, что `router/luna` и `router/sol` по-прежнему обходят автоматическую оценку.

**Критерий готовности:** тесты воспроизводят текущее «залипание» Sol и защищают оба направления переключения.

### 2. Оценивать только текущий пользовательский запрос

- Для строкового `input` сохранить текущее поведение.
- Для массива `input` анализировать последнее сообщение с `role: "user"`.
- Игнорировать предыдущие пользовательские сообщения, developer/system-контекст и tool items.
- Сохранить текущий формат `RoutingDecision`: `target`, `score`, `reasons`.

**Критерий готовности:** в одной Codex-сессии маршрутизация корректно переключается Sol → Luna и Luna → Sol при изменении сложности последнего запроса.

## Приоритет 1 — улучшение детерминированной эвристики

**Статус: выполнен.**

### 3. Перейти от поиска подстрок к набору признаков

- Искать слова и фразы по границам, чтобы уменьшить ложные совпадения.
- Учитывать структурные признаки: количество путей к файлам, блоков кода, stack trace и отдельных требований.
- Разделить признаки на группы: риск, область изменений, архитектура, диагностика и простые локальные действия.
- Начислять балл группе один раз, независимо от повторения одного слова.
- Добавить бонусы за сочетания, например архитектура + несколько модулей или диагностика + stack trace.
- Добавить отрицательные баллы для очевидно локальных задач: typo, rename, formatting.

**Критерий готовности:** решение зависит от нескольких независимых признаков, а `reasons` показывает вклад каждой сработавшей группы.

### 4. Создать проверочный набор маршрутизации

- Собрать небольшой набор обезличенных примеров простых, пограничных и сложных задач.
- Для каждого примера зафиксировать ожидаемую модель и причины.
- Добавить проверки ложного выбора Sol и ложного выбора Luna.
- Не использовать сообщения одной сессии одновременно как независимые обучающие и проверочные примеры.

**Критерий готовности:** изменение весов и порога можно оценить на стабильном наборе сценариев до выпуска.

## Приоритет 2 — подготовка обучаемого маршрутизатора

### 5. Определить формат данных

- Хранить текущий пользовательский запрос, результаты Luna и Sol, предпочтительную модель и способ оценки.
- Для программных задач предпочитать объективную оценку через тесты, сборку и typecheck.
- Сделать сбор пользовательских промптов только явным и отключённым по умолчанию.
- Не записывать секреты и полный prompt в обычные routing-логи.
- Для MVP использовать версионируемую запись schemaVersion: 1 с запросом, результатами Luna/Sol, предпочтительной моделью и методом оценки.

**Критерий готовности:** формат позволяет обучать модель на предпочтении Luna/Sol без изменения production API.

### 6. Проверить RouteLLM-подобный прототип

- Обучать маршрутизатор offline, отдельно от Node.js runtime.
- Начать с компактной линейной модели и экспортировать веса в JSON.
- Подключить модель как новую реализацию `RoutingStrategy` с эвристикой в качестве fallback.
- Сначала запускать её в shadow-режиме без влияния на реальные запросы.
- Сравнивать качество, долю вызовов Sol и задержку с детерминированной эвристикой.

**Критерий готовности:** обучаемый маршрутизатор превосходит эвристику на проверочном наборе и не добавляет существенную задержку.

## Порядок выполнения

1. Регрессионные тесты накопленного контекста.
2. Анализ только последнего пользовательского сообщения.
3. Структурные и комбинационные признаки.
4. Стабильный проверочный набор.
5. Формат и безопасный сбор данных.
6. Offline-прототип обучаемого маршрутизатора.

## Не делать на первых этапах

- Не подключать RouteLLM или AutoMix как отдельный runtime-сервис.
- Не добавлять embeddings, векторную базу, GPU или дополнительную генеративную модель.
- Не реализовывать AutoMix-проверку ответа до стабилизации обычной маршрутизации.
- Не сохранять выбранную модель как состояние сессии.
